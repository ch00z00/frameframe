# Requirements Document

## Project Description (Input)
記事の表示パイプライン（article-rendering）: Astroプロジェクトの土台となる、MDX記事のContent Collections定義、記事詳細ページ、トップの記事一覧、タグ別の静的一覧ページ。記事コンテンツはsrc/content/articles/配下のMDXファイルとして管理し、frontmatterでtitle/tags/is_premiumなどを持つ。記事本文からは自作コンポーネント（比較表・引用ブロックなど）を埋め込める。スタイリングは素のCSS（デザイントークン）。検索(Pagefind)は本specの範囲外とし、後続specで扱う。

## Introduction

本機能は FrameFrame サイトの土台となる「記事の表示パイプライン」を構築する。旧作・名作映画の批評記事を MDX ファイルとして管理し、それを記事詳細ページ・トップの記事一覧・タグ別一覧ページとして静的生成する。記事本文には比較表や引用ブロックといった自作コンポーネントを埋め込め、スタイリングは素の CSS（デザイントークン）で行う。

このパイプラインが完成することで、ライター（当面は運営者本人）は MDX ファイルを追加するだけで記事を公開でき、読者は一覧・タグ・記事詳細を回遊できるようになる。ローンチ要件である「10本以上の記事を揃えた公開」の前提となる基盤であり、後続の検索機能（Pagefind）やマネタイズ機能はこの記事データモデルの上に構築される。

### スコープ外（本 spec では扱わない）

- 全文検索（Pagefind）— 後続 spec で扱う
- 監督・俳優・ロケーションの独立した一覧/詳細ページ（`product.md` の方針により恒久的に対象外）
- 認証・課金・有料記事の本文ゲート（`is_premium` フラグの定義のみ行い、ゲート処理は将来 spec）
- コメント、いいね等の読者インタラクション機能
- 記事の CMS 的な編集 UI（MDX ファイルの直接編集で運用）
- Vercel へのデプロイ設定（別途対応）

### 用語

- **公開記事**: `draft` が false であり、かつ `publishDate` が本番ビルド時点の日時以前である記事。一覧・タグページ・sitemap 等に載るのはこの条件を満たす記事のみ。
- **プレビュー実行**: ローカル開発サーバーでの表示。draft や未来日の記事も確認できる。

## Requirements

### Requirement 1: コンテンツコレクションとスキーマ定義

**目的:** ライターとして、記事を型検証された MDX ファイルとして一元管理したい。これにより frontmatter の書き間違いをビルド時に検出でき、記事データが一貫した構造を保てる。

#### 受け入れ基準

1. `src/content/articles/` 配下に配置された MDX ファイルは、記事コンテンツコレクションの 1 エントリとして認識される。
2. 記事コンテンツコレクションは、各記事の frontmatter に対して次のフィールドを定義する。
   - `title`（必須・文字列）
   - `description`（必須・文字列）
   - `publishDate`（必須・日付）
   - `updatedDate`（省略可・日付・最終更新日）
   - `tags`（必須・文字列配列）
   - `is_premium`（省略可・真偽値・既定 false）
   - `draft`（省略可・真偽値・既定 false）
3. 記事の frontmatter が必須フィールドを欠く場合、または定義された型と一致しない場合、ビルドは失敗し、対象ファイルと問題のあるフィールドを示すエラーが出力される。
4. `tags` 配列に空文字列または重複した値が含まれる場合、ビルドは失敗する。
5. 各記事を一意に識別する slug は、MDX ファイル名から導出される。

### Requirement 2: 記事詳細ページ

**目的:** 読者として、個々の批評記事を読みやすいレイアウトで閲覧したい。これにより記事本文と、それを補強する付随情報（タグ・公開日など）を一度に把握できる。

#### 受け入れ基準

1. 公開記事は、`/articles/<slug>/` のパスで静的に生成される。
2. 記事詳細ページは、記事の `title`、`publishDate`、`tags` を本文の冒頭に表示する。
3. 記事に `updatedDate` が設定されており、かつ `publishDate` と異なる場合、記事詳細ページは最終更新日を併記する。
4. 記事詳細ページは、MDX 本文を HTML としてレンダリングし、Markdown 記法（見出し、強調、リンク、リスト、画像、引用）を反映する。
5. 記事詳細ページは、記事に付与された各タグから、対応するタグ別一覧ページ（Requirement 4）へのリンクを提供する。
6. 存在しない slug へのリクエストに対しては、404 応答を返す。
7. 記事に、他の記事と共通するタグが存在する場合、記事詳細ページは同じタグを持つ他の記事への導線（関連記事リンク）を最大 N 件表示する。（N は設計フェーズで確定）

### Requirement 3: トップページ（記事一覧）

**目的:** 読者として、サイトを訪れたときに掲載記事の全体像を把握したい。これにより興味を持った記事に素早くたどり着ける。

#### 受け入れ基準

1. ルートパス `/` に、公開記事の一覧が静的に生成される。
2. トップページは、公開記事を `publishDate` の新しい順に並べる。
3. トップページは、各記事について `title`、`description`、`publishDate`、`tags` を表示し、記事詳細ページへのリンクを提供する。
4. 公開記事が 1 件も存在しない場合、トップページは記事がない旨のプレースホルダー表示を行い、ビルドは成功する。
5. 記事一覧の件数が閾値を超える場合、トップページはページネーションまたは表示件数の上限を適用する。（閾値・方式は設計フェーズで確定）

### Requirement 4: タグ別一覧ページ

**目的:** 読者として、関心のあるテーマ（監督名・年代・ジャンル等のタグ）に沿って記事を絞り込みたい。これにより特定の切り口で記事群を回遊でき、検索エンジンからのロングテール流入の入口にもなる。

#### 受け入れ基準

1. 公開記事のいずれかに付与されているタグごとに、`/tags/<tag>/` のパスでページが静的に生成される。
2. タグ別一覧ページは、そのタグを持つ公開記事のみを `publishDate` の新しい順に一覧表示する。
3. タグ別一覧ページは、対象タグ名と、そのタグに属する記事件数を表示する。
4. 公開記事に一度も使われていないタグについては、ページを生成しない。
5. 全タグを一覧できるインデックス（`/tags/`）が静的に生成され、各タグページへのリンクと記事件数を表示する。
6. タグ名に URL で扱えない文字が含まれる場合、タグ名を安全にスラッグ化した上でページを生成し、表示上は元のタグ名を用いる。

### Requirement 5: 記事内の自作コンポーネント（リッチ表現）

**目的:** ライターとして、記事ごとに論の見せ方を変えられるようにしたい。これにより「なぜこの作品が優れているか」を、比較表や引用など内容に合った形式で提示できる。

#### 受け入れ基準

1. `src/components/` 配下に、MDX 本文から `import` して利用できる自作コンポーネント群が提供される。
2. 自作コンポーネント群は、少なくとも「比較表」および「引用ブロック（出典付き）」の 2 種を含む。
3. MDX 本文中で自作コンポーネントが利用されている場合、記事詳細ページはそのコンポーネントを本文の該当位置にレンダリングする。
4. 自作コンポーネントは、デザイントークン（Requirement 6）を参照してスタイリングされ、ライト / ダーク両テーマで破綻しない。
5. MDX 本文が参照するコンポーネントの import が解決できない場合、ビルドは失敗し、対象記事が示される。
6. 自作コンポーネントの追加は、既存記事のビルドに影響を与えない。

### Requirement 6: 共通レイアウトとデザイントークン

**目的:** 読者として、どのページでも一貫した視覚的トーンと可読性で閲覧したい。ライターとして、色・タイポグラフィを一元管理したい。

#### 受け入れ基準

1. `src/styles/tokens.css` に、色・タイポグラフィ・余白のデザイントークンが CSS カスタムプロパティとして定義される。
2. 全ページで共通のベースレイアウト（ヘッダー、フッター、本文コンテナ）が適用される。
3. 閲覧環境がダークモードを要求している場合、ダーク用に再定義したトークン値が適用される。明示的なテーマ指定がある場合はそれを優先する。
4. ユーティリティ CSS フレームワークおよび Sass は使用しない。
5. 本文の行長・行間は、長文読書に適した値に設定される。
6. ベースレイアウトは、キーボード操作時にフォーカス可能要素の可視状態を提供する。

### Requirement 7: SEO・メタデータ・配信最適化

**目的:** 運営者として、記事が検索エンジンと SNS で正しく扱われるようにしたい。これにより SEO 主体の集客戦略が機能する。

#### 受け入れ基準

1. 記事詳細ページは、記事の `title` を `<title>` に、`description` を meta description に出力する。
2. 記事詳細ページは、Open Graph（`og:title`、`og:description`、`og:type`、`og:url`）および Twitter Card のメタタグを出力する。
3. 全ページに正規 URL（canonical link）が出力される。
4. 公開記事を対象とした `sitemap.xml` が、ビルド時に生成される。
5. 記事詳細ページは、記事を表す構造化データ（JSON-LD, 例: Article / BlogPosting）を出力する。
6. `draft: true` の記事は、sitemap・一覧・タグページ・OGP のいずれにも含まれない。

### Requirement 8: 公開状態の管理（draft / is_premium）

**目的:** ライターとして、執筆途中の記事を公開せずに管理し、将来の有料化に備えたフラグだけ先に持たせておきたい。

#### 受け入れ基準

1. 本番ビルドでは、`draft: true` の記事は一覧・タグページ・記事詳細のいずれとしても生成されない。
2. プレビュー実行では、`draft: true` の記事も閲覧可能になる。
3. 記事コンテンツコレクションは `is_premium` フラグを保持するが、本 spec の範囲では全記事を無料として扱い、本文の出し分けは行わない。
4. 全記事の `is_premium` が false である間は、有料に関する UI 表示を一切行わない。
5. 本番ビルドでは、`publishDate` が未来日の記事を公開扱いにしない。
6. プレビュー実行では、`publishDate` が未来日の記事も閲覧可能になる。

### Requirement 9: ビルドとローカル開発

**目的:** ライターとして、記事を追加したらローカルで確認し、問題なければそのまま静的サイトとしてビルドできる状態にしたい。

#### 受け入れ基準

1. FrameFrame プロジェクトは、リポジトリルートに Astro プロジェクトとして構成され、`package.json` に開発サーバー起動とビルドのスクリプトを持つ。
2. ローカル開発サーバーを起動すると、記事・一覧・タグページが閲覧可能な状態で提供され、MDX ファイルの変更が反映される。
3. 本番ビルドを実行すると、全ページが静的 HTML として `dist/` に出力される。
4. Astro プロジェクトは、既存の `docs/`（開発ログ）・`.claude/`・`.kiro/` ディレクトリと共存し、それらをビルド出力に含めない。
5. クライアントサイド JavaScript は、明示的に必要なコンポーネント以外には出力されない。
6. ビルド成果物（開発時の一時ファイル・`dist/` 等）は、Git 管理対象から除外される。
